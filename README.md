# 舞台提示执行台

本地单人使用的舞台提示（cue）执行台：开场前录入 2～12 条按顺序排列的提示，演出中逐条确认发出；演出中可随时改写或重排尚未发出的提示，已发记录保持原样。**没有控制权的页面还能为待发提示提交"改写提议"**：只保存建议与原文快照、不动提示，由控制席凭最新版本审核接受或拒绝，接受才真正改写。已结束或提前收场的演出可**归档本场**，保存为独立档案，下一场开始后仍可随时回看。演出中还可开启**自动发出**：按统一间隔（1～60 秒）由服务端后台自动确认当前提示，暂停、核验就绪门槛与手工操作都会正确衔接，无需页面保持打开。

另有**双页设计**：执行台页（`/`）供舞台监督操作（提示正文、核验、自动发出等后台信息只在这页）；观众可在独立设备 / 标签页打开**观众字幕屏**（`/screen`）——整页只显示执行台**另行设置、随发出上屏**的字幕，永远不显示后台提示正文；该页经只读接口 `GET /api/screen` 轮询，只拿到字幕与一个跨场不归零的递增画面序号。

技术栈：Python / FastAPI + SQLite + 原生 HTML/CSS/JavaScript（无前端构建步骤）。

## 启动（一条命令）

```bash
docker compose up --build
```

- 访问地址：**http://localhost:8000**
- 端口：**8000**
- 停止：`Ctrl + C`
- 数据保存在 Docker 卷 `cue-data` 中，刷新页面、重启容器/服务都不会丢失提示顺序与进度。

## 本地运行（不用 Docker）

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

同样访问 http://localhost:8000 。数据库文件默认在 `app/data/cues.db`，可用环境变量 `DB_PATH` 覆盖。

## 使用流程

1. **开场前设置**：录入 2～12 条提示，每条需唯一编号 + 非空内容，顺序即发出顺序；点击「开始演出」。
2. **演出中**：页面突出显示**当前待发**提示与**下一条**，右侧为**已发记录**。
   - 「确认发出」：服务端把**那一刻**的内容记入已发并推进一条；全部发出后显示完成横幅。
   - **撤回末条 ↩**：误点确认后可把**本场最后一条已发提示**退回当前待发补救，**不撤销其他操作**。已发记录标题右侧的「撤回末条」会先弹**二次确认**，确认后提交页面所见的末条提示 `cue_id` 与版本号：该提示按**发出时的内容快照**退回为**当前待发（现有待发队首）**，**保留原 id 与编号**，其发出快照、发出时间与发出序号一并清除；**其他已发记录、待发内容与相对顺序、现场问题记录快照均不变**。仅**演出中（含暂停时）或已完成**且该 id 仍为最后已发提示时生效；**完成态撤回后回到演出中**，**暂停标记不变**（暂停时撤回后仍需先恢复才能再次发出），该提示**再次确认时记新的服务端时间**。
   - 「暂停发出 ⏸」：演出中可随时暂停（如处理突发情况），处理完后点「恢复发出 ▶」继续。暂停**不清空提示、不推进进度**；暂停期间页面显示暂停标记、确认按钮禁用（接口同样拒绝），**改写、重排、撤回末条、归档仍可用**，恢复后按暂停期间改过的最新顺序和内容继续。暂停标记保存在数据库中，刷新页面或重启服务后仍保留。
   - 待发列表中可**改写**（编号/内容）或用 ↑↓ **重排**任何尚未发出的提示；已发记录不可更改。
   - **现场问题记录**：演出中（含暂停时）或全部发出完成后，点任意已发或待发提示后的 **⚠** 即可为**该条提示**追加一条现场问题（去除首尾空白后 1～200 字符）。记录保存**服务端时间、当时编号、内容快照与已发／待发状态**——已发提示取**发出时的内容快照**，此后不受编辑影响；待发提示取记录时的当前编号与内容。记录按**保存顺序**列在右侧「现场问题」，随页面状态与档案详情读取，**不提供单条修改或删除**；记录只令版本号 +1，**不推进提示、不改变暂停状态**。开场前不能记录。
3. 「重新开始」清空进度，回到设置页。
4. **归档本场**：演出中（提前收场）或全部发出（已结束）时，点击演出页的「归档本场」，输入非空的**场次名称**后保存：
   - 档案记录归档时间、当时状态（已完成 / 提前收场）、**按发出顺序**排列的已发编号、内容快照与发出时间，**按待发顺序**排列的剩余编号和内容，以及**按保存顺序**排列的本场**现场问题记录**（含服务端时间、当时编号、内容快照与已发／待发状态）；
   - 保存档案与清空当前提示、**问题记录**在**同一事务**内完成：保存失败不会清空任何当前数据；成功后回到开场前设置、版本号 +1，可立即录入下一场；
   - 开场前（设置页）不能归档；**同版本的归档与确认/编辑等操作只有一个生效**，重复提交因版本过期返回 `409`，不会多建档案。
5. **回看档案**：点击右上角「📚 档案库」查看列表（含名称、归档时间、状态、已发／剩余／问题条数，按归档时间倒序、同时间按档案 ID 倒序），点击任意一条查看已发快照、剩余未发与**现场问题记录**详情。后续录入、重置和重启服务都不会改变已有档案。
6. **以此开新场**：在**档案详情**中点击「以此开新场 ▶」并确认，即可以档案为底稿直接开始下一场：
   - 先取档案中**按发出顺序**排列的已发编号与**内容快照**（页面所见版本，不含发出时间），再接上**按待发顺序**排列的剩余编号与内容，全部作为新场的**待发提示**，顺序即新场发出顺序；
   - 成功后直接进入**演出中**：已发为空、当前指向第一条、版本号 +1；不继承旧场的发出时间、进度或**现场问题记录**（不复制问题记录），**原档案不做任何修改**；刷新页面或重启服务后新场状态仍保留；
   - 仍需满足 2～12 条、编号唯一、内容非空的规则（正常归档得到的档案天然满足）；**仅开场前（设置页）允许生效**，演出中/已完成时按钮禁用。
7. **场次对照**：在档案库列表点击「场次对照 ⇄」，分别选择**基准场次**与**对照场次**，即可并排查看两场提示的发出节奏差异：
   - 按**编号精确匹配**取两场提示的并集，按编号字符串升序列出；每条显示两侧的**内容快照**、**已发 / 未发 / 缺失**状态，以及**相对发出秒数**（各场以首条已发提示的发出时间为零点，保留毫秒，暂停时长计入；未发、缺失或整场无已发记录时显示 `—`）；
   - 仅当两侧**均已发出且内容完全一致**时，计算「对照 − 基准」的秒数差（**正值表示对照场更晚**），其余情况显示 `—` 及原因；没有可对照的编号时页面会给出提示；
   - 切换任一场次会立即清空旧结果并重新查询，较慢的旧响应不会覆盖新结果；对照是**只读查询**，不修改档案、当前演出或版本号，任意演出状态下都可使用。
   - 档案弹窗的每个视图（列表 / 详情 / 归档表单 / 对照）都有视图序号：切换视图或关闭弹窗即作废旧视图未完成的请求，迟到的响应（无论成功、空列表还是失败）不会改写当前标题、页面、场次选择或对照结果，也不会触发默认组合查询；当前视图的加载失败仍正常显示错误。
8. **单控制席（可选）**：默认未启用，所有页面均可写（旧行为不变）。需要多人现场防误触时，任意页面点击右上角「启用控制席」即可启用：
   - 启用成功返回一把**随机凭据**，仅保存在**本标签页**（sessionStorage），此后该标签页的写操作自动经请求头 `X-Control-Token` 提交；其他标签页/设备变为**只读**（写按钮禁用），但仍可查看状态与档案；
   - 其他页面可随时点「接管控制席」**主动接管**：凭当前版本号换发新凭据，**原控制席的凭据立即失效**，其后续写操作被 `403` 拒绝（即使用最新版本号也不能写）；
   - 页头始终显示本页控制资格（未启用 / 本页 ✓ / 他人·只读）。资格以**服务端核验**为准：页面启动时自动把本标签页缓存的凭据随 `GET /api/state`（请求头 `X-Control-Token`）提交核验，按响应的 `control_granted` 更新标记与全部写入口——**被接管后的旧标签页刷新即显示只读并露出接管入口，本地失效凭据同时被清除，无需先触发一次 403**；凭据仍有效则刷新后照常可写；写请求收到 `403` 时同样自动纠正。凭据与启用状态保存在数据库中，**跨场、刷新页面、重启服务都保留**；不提供账号、超时或关闭功能。
9. **本场核验（可选）**：默认关闭。需要灯光、音响分别确认"当前提示已就绪"才能发出的场次，**开场前**在设置页点击「启用本场核验」（凭当前版本号，受控制席保护，版本 +1）：
   - 演出页显示**当前轮次**与**灯光 / 音响两工种**的就绪状态（未回报 / 未就绪 / 就绪 ✓）；两工种的页面（**只读页也可以**）直接点自己工种的「报就绪」即可回报，再点一次取消；也可由任意客户端调 `POST /api/verify/report` 提交**工种、`cue_id`、轮次与就绪布尔值**——**无需控制凭据、不改全局版本号**；该接口接受**可选**请求头 `X-Control-Token`：缺失或已被接管替换的凭据照样可回报、不会收到 `403`（不获得控制权），但成功响应与 `409` 附带状态中的 `control_granted` 都按**本次请求凭据**如实回报且不泄露凭据——**当前控制席回报后本页资格与 sessionStorage 凭据保留、页面不变只读**，两工种就绪且未暂停时可直接确认；被接管的旧页回报后按真实资格清除失效缓存；
   - **回报按钮状态衔接**：请求在途时灯光/音响两个回报按钮统一禁用以防重复回报；请求结束（成功、`409` 刷新为最新状态、网络失败或其他错误）后一律按**当时最新状态**重新计算是否可点——不会因一次请求（含开场成功后的首次渲染）永久禁用；
   - 仅**演出中（含暂停）**接受对**当前提示 + 当前轮次**的回报，过期返回 `409` 及最新状态；同工种同轮次重复回报以最后一次为准；**暂停时可回报但不能发出**；**完成收场（无当前提示）或核验关闭后不可回报**；
   - 两工种**都报就绪**后「确认发出」才可用（否则按钮禁用、接口返回 `409` 及最新状态）；**确认推进、撤回末条、改写当前提示、重排更换当前提示都会开启新轮次并清空本轮就绪**（轮次单调递增、不可复用，旧轮次回报被 `409` 拒绝）；**编辑其他提示、暂停/恢复、接管不清空**；
   - 轮次与就绪记录保存在数据库中，**刷新页面、重启服务都保留**；**归档或重置会关闭核验并清空轮次与就绪，下一场不继承**（需要时重新在开场前启用），档案结构不变；核验关闭时所有接口保持旧行为。
10. **自动发出（可选）**：默认关闭。演出中在「自动发出」卡片输入 1～60 秒整数间隔后点「开启自动 ▶」（或调 `POST /api/auto`，携带版本号、受控制席保护，成功版本 +1）：
   - 开启或改间隔后**从完整间隔重新计时**；服务端后台任务在**当前提示等满间隔、未暂停且核验门槛满足**时自动发出一条（与手工确认同样的内容快照、版本推进与换轮规则），**每次只发一条、不补发积压**，无需页面保持打开；
   - **暂停冻结剩余时间、恢复续计**；到期未就绪（核验未齐）**继续等**，就绪后随即发出；**手工确认、撤回末条、改写当前提示、重排换头都会重新计时**，队首不变的重排与编辑其他提示不重置；
   - **接管控制席、归档、重置、全部发出完成或服务重启都会关闭自动模式**（已设间隔保留）；页面每秒轮询同步进度，卡片显示开关、剩余秒数或「等待就绪」，手工确认等旧操作不受影响。
11. **改写提议（无控制权页可提交，控制席审核）**：演出中（含暂停时）任何页面点任意**待发提示**后的 **💡**，即可为该提示提交一条改写建议（或调 `POST /api/suggestions`，提交 `cue_id`、建议内容与页面所见 `version`）：
    - 提交只保存**当时原文快照**与建议内容，**不改动提示、不推进版本号**，也**不需要控制凭据**（只读页同样可提交，永不 `403`；建议内容去除首尾空白后须非空，否则 `400`）；仅**演出中（含暂停）的待发提示**可提交，开场前、目标已发出或版本过期返回 `409`，提示不存在 `404`；
    - 右侧「改写提议」列表按提交顺序展示每条提议的**原文、建议与处理状态**（待审核 / 已接受 / 已拒绝，待审的还会提示目标是否仍与原文一致）；**控制席**对每条待审提议点「接受 ✓」或「拒绝 ✕」（`POST /api/suggestions/{id}/accept`、`/reject`，携带最新版本号、受凭据保护），只读页只能提交、不能审核；
    - **接受**：目标提示必须**仍是待发**且当前内容**等于原文快照**——**其他提示的编辑、暂停、重排（含把它换位置）都不使提议失效**；只有该提示自身被改写（内容已变）或已被手工 / 自动确认发出，接受才返回 `409` 且提议保持待审（仍可拒绝）。接受时「**写入建议内容 + 标记已接受 + 版本 +1**」在同一事务完成；接受的是**当前提示（待发队首）**时同时**重开核验轮次、清空就绪并重新自动计时**，接受其他提示不重置；
    - **拒绝**：只把提议标记为已拒绝，**不改提示、不改版本号**；目标已失效也能直接拒绝；
    - 版本过期、提议不存在或已处理（接受 / 拒绝）都返回 `409` 及最新状态、提议不变；与确认、编辑、重排、撤回、暂停、归档以及手工 / 自动发出交错时，锁 + 版本 + 快照检查保证**不重复处理、不覆盖已变内容、不留半次结果**，任一步写入失败整体回滚；
    - 提议记录保存在数据库中，**刷新页面、重启服务都保留**；**归档、重置、开新场（手工录入或以档案开新场）一并清空，不写入档案**。
12. **观众字幕屏（双页使用）**：执行台为提示**另行设置观众字幕**，与提示正文相互独立；观众打开 `/screen`（也可点执行台页右上角「🖥 观众字幕屏」新开标签页）只看到字幕，看不到任何后台提示正文。
    - **设置（执行台）**：演出中点任意**待发提示**后的「字幕」即可填写（或调 `POST /api/subtitles`，携带 `version`、`cue_id` 与 `subtitle`），去除首尾空白后 **1～200 字符**，传 `null` 为清除；携带版本号、**受控制席保护**，设置与版本 +1 在同一事务保存。设置**只保存字幕本身**：不推进提示、不换核验轮次、不重新自动计时，也**不立即改变观众画面**；非法文本返回 `400`，非演出中（开场前 / 已完成）、目标非待发或版本过期返回 `409` 及最新状态。暂停期间同样可以设置。
    - **绑定与失效**：字幕绑定**提示身份（cue_id）**。**手工编辑或接受改写提议改写该提示（即使新文本与原文完全相同）都会使字幕失效**，执行台待发列表以「字幕 ✓ / 字幕已失效」标记如实展示设置与有效性（设置文本保留，可重新设置恢复有效）；**重排、暂停、记现场问题、撤回都不影响字幕**。
    - **上屏 / 清屏**：手工确认或自动发出一条提示时，**有效字幕随发出在同一事务替换观众画面**；没有字幕或字幕已失效则**清屏**。画面与发出一起保存、任一失败整体回滚（字幕问题**不会额外阻挡发出**）。**撤回**末条时**清屏但保留字幕设置**（撤回回到待发的提示仍带着它的字幕与有效性，再次发出照常上屏）；**归档、重置、手工录入新场、以档案开新场清屏并清除全部字幕设置**，字幕**不写入档案**。
    - **观众只读页**：`/screen` 每秒轮询 `GET /api/screen`，响应**只有** `subtitle`（当前字幕，清屏为 `null`）与 `seq`（**跨场不归零、画面内容每次变化都 +1 的递增序号**），不含提示正文、编号、进度、版本号、控制席等任何后台信息，也不需要凭据。页面**只接受更大的 `seq`**：乱序或迟到的旧响应（含清屏前最后一帧字幕）一律丢弃，**画面不会倒退**；断线时保留最后一帧并提示重连，不自动清屏。
    - 字幕设置与观众画面都保存在数据库中，**刷新页面、重启容器 / 服务都保留**；旧版本数据库启动时自动加列，旧库默认无字幕设置、画面为空、序号 0。字幕**不写入档案**，档案 JSON 结构不变；既有接口、字段与状态码保持兼容（`GET /api/state` 的待发条目新增 `subtitle` / `subtitle_valid`，整体状态新增 `screen`）。

## 并发与一致性规则

### 改写提议（提交 / 接受 / 拒绝）

- **提交（`POST /api/suggestions`）**：无控制权页面（只读页）也可提交，**不需要也不校验控制凭据，永不返回 `403`**；接受可选的 `X-Control-Token`，成功响应的 `control_granted` 按本次凭据如实回报（与工种回报一致）。请求体为 `{version, cue_id, content}`：建议内容去除首尾空白后须非空（沿用 `/api/edit` 校验，否则 `400`，先于版本检查、不写入）；仅**演出中（`live`，含暂停）**且目标提示**仍为待发**时接受，开场前 / 已发出 / 版本过期返回 `409`，提示不存在 `404`。提交在锁内只做「读取当前编号与内容 → 保存原文快照 + 建议」，**不改提示、不改版本号**；写入失败整体不变。
- **接受（`POST /api/suggestions/{id}/accept`）**：控制席操作，携带最新 `version` 与凭据，缺失 / 失效凭据 `403`。锁内顺序检查版本 → 提议存在且仍为 `pending` → 目标提示仍为 `pending` 且**当前内容等于原文快照**：版本过期、提议不存在 / 已处理（已被接受或拒绝）、目标已发出或内容已变，都返回 `409` 及最新状态且**提议保持不变**。**其他提示的编辑、暂停 / 恢复、重排（含把该提示换到队首 / 别处）不使提议失效**；目标提示自身被改写（内容不再等于快照）或被手工 / 自动确认发出才失效。「UPDATE 提示内容为建议 + 标记提议 `accepted` + 版本 +1」在同一事务提交；接受的是**当前提示（待发队首）**时一并**重开核验轮次、清空本轮就绪、重新自动计时**（与 `/api/edit` 改写当前提示完全一致），接受其他提示不重置轮次 / 计时。
- **拒绝（`POST /api/suggestions/{id}/reject`）**：控制席操作，携带最新 `version` 与凭据；只把提议标记为 `rejected`，**不改提示、不改版本号、不重置轮次 / 计时**。不校验目标快照（目标已改 / 已发出也可拒绝）；版本过期、提议不存在或已处理返回 `409`。拒绝不推进版本，因此同版本的拒绝与一次业务写操作不构成版本竞争，但与同版本的**接受**竞争时先到者生效、后到者以「提议已处理」拿到 `409`。
- **交错安全**：提交 / 接受 / 拒绝与确认、撤回、编辑、重排、暂停、归档、问题记录、接管、手工 / 自动发出共用同一把写锁与同一版本号：接受与任何业务写同版本竞争最多一个成功；提示被自动发出后，迟到的接受以「目标已非待发」返回 `409`，不会把建议写到别的提示上；重复点击接受 / 拒绝第二次必为 `409`（状态已非 `pending`），不重复处理。接受事务任一步失败（如注入的 UPDATE 触发器）整体回滚：提示、提议状态、版本全部不变。
- **生命周期**：提议随数据库持久化，**刷新页面、重启服务保留**；**归档、重置、手工录入新场、以档案开新场在同一事务内清空**，提议**不写入档案**（档案 JSON 结构不变，档案接口不返回 `suggestions`）。状态接口 `GET /api/state` 的 `suggestions` 字段按提交顺序返回全部提议（含已接受 / 已拒绝），每条含 `cue_id`、提交时编号 `cue_number`、`original_content`（原文快照）、`content`（建议）、`status`（`pending` / `accepted` / `rejected`）、派生字段 `target_valid`（仅待审时可能为 `true`：目标仍待发且内容等于快照）、`created_at` 与 `decided_at`。

### 版本号与既有操作

- 页面上的每次确认 / 编辑 / 重排 / 归档都携带页面当前看到的**版本号**。
- 服务端每次成功变更都会把版本号 +1；携带过期版本号的请求返回 `409` 并附带最新状态，页面随即刷新显示。
- 因此：**同一版本的两个操作只有一个生效**；**重复点击不会跳过提示**（按钮在请求在途时禁用，且第二次点击的版本号已过期）；**编辑胜出后，基于旧内容的确认会被拒绝**；**重复提交归档不会多建档案**。
- 确认发出的内容以服务端当时存储的内容为准并快照保存，已发记录此后不受编辑/重排影响。
- **撤回末条**（`POST /api/withdraw`）提交页面所见的**末条已发 `cue_id`** 与版本号，在锁内检查：仅演出中（`live`，**含暂停时**）或已完成（`done`）、版本匹配**且该 id 仍是最后一条已发提示**时才生效。执行时以**发出快照**作为待发内容（保留 id 与编号），**清除发出快照、发出时间与发出序号**，把该提示插到**现有待发队首**（现有待发内容与相对顺序整体后移）；**其他已发记录、待发内容与相对顺序、问题记录快照都不变**。「退回待发（位置/内容/清空发出字段）+ 完成态回到演出中 + 版本 +1」在**同一事务**内提交，**写入失败则全部不变**；**完成态撤回后状态回到演出中，暂停标记保持不变**（暂停时撤回后仍暂停），该提示再次确认时记**新的发出时间**。**版本过期、目标不是末条（已被先撤回）或本场没有已发提示都返回 `409`** 及最新状态。因此撤回与确认、编辑、重排、归档、暂停/恢复、问题记录**同版本竞争最多一个成功**；只能撤最后一条，**不提供批量撤回或重做**。撤回结果随数据库持久化，**刷新、重启保留**，**既有档案不受影响**。
  - **待发位置分配（位置溢出修复）**：撤回插入队首与重排后，服务端都会对**全部待发提示按当前显示顺序重新分配紧凑位置 `1..n`**（每场最多 12 条，位置恒为小整数）。旧实现以 `MAX(position)+1` 为基数平移/追加位置，反复"确认 → 撤回"同一提示会让位置近似指数增长——把待发重排后，**累计第 61 次撤回**时位置越过 SQLite 有符号整数上限（`2^63-1`）被舍入成同值浮点，`ORDER BY position` 退回按 id 排序，待发顺序被悄悄改写（如 `A1、A3、A2` 错成 `A1、A2、A3`）；不重排时**第 62 次撤回**直接抛 `OverflowError`。新分配方式**不限制操作次数、不吞掉异常**（真实写入失败仍随事务回滚并返回错误），反复确认/撤回任意次数顺序都不再改变；**既有库中已接近 SQLite 整数上限但仍可区分的位置也能正常撤回**（撤回后即被压实为小整数；已溢出成同值浮点而丢失的历史顺序不恢复）。
- 暂停/恢复同样携带页面版本号：**仅演出中**且目标状态与当前不同时生效，「暂停标记 + 版本号 +1」在同一事务内落库，写入失败两者都不变；**非演出中、目标已达成（如已暂停时再暂停）或版本过期都返回 `409` 及最新状态**。因此**同一版本的暂停、恢复、确认和编辑最多一个生效**。
- 暂停期间「确认发出」即使用最新版本号也返回 `409` 及最新状态；编辑、重排、撤回末条、归档不受影响，撤回末条不改变暂停标记。归档、重置、录入新场、以档案开新场**成功后一律回到未暂停**；这些操作失败时保留原状态，既有档案不变。旧版本数据库启动时自动补上暂停标记列，默认未暂停。
- **现场问题记录**（`POST /api/issues`）同样携带页面版本号并在锁内检查：仅演出中（含暂停时）或已完成可记录，**开场前返回 `409`**；正文去除首尾空白后须为 **1～200 字符**，否则返回 `400`（先于版本检查，不改数据）；提示不存在返回 `404`。「插入记录 + 版本 +1」在同一事务内提交，**不推进提示、不改变暂停状态**，失败时记录与版本都不变。因此**同版本的问题记录与确认、暂停／恢复、编辑、重排、归档最多一个成功**。已发提示保存其**发出快照**（编号与内容此后不可变），待发提示保存记录时的编号与内容；之后的编辑不改已保存的记录快照。
- 归档的「写档案 + 清空提示 + 版本 +1」在同一数据库事务内提交，任一步失败整体回滚，不会出现档案没存上、提示却被清空的情况。
- 「以此开新场」同样携带页面版本号并在锁内检查：**非开场前或版本过期返回 409**（附最新状态），同版本的重复点击或并发提交最多一次生效；「写入新场提示 + 进入演出中 + 版本 +1」在同一事务内提交，失败时当前场次与档案都不变。
- 档案独立于当前场次存储：录入新场次、重新开始（重置）、以档案开新场、重启容器/服务都不会修改或删除档案；旧版本数据库启动时会自动创建档案表与问题记录表、为旧档案补上问题记录列（旧档案默认无记录），可直接使用。
- 现场问题记录与当前场次同库持久化：**刷新页面、重启容器/服务都保留**；归档时随本场快照**一起写入档案并清空当前记录**，重置、手工录入新场、以档案开新场也会清空当前记录（以档案开新场**不复制**档案中的问题记录，原档案保持不变）。记录只增不改不删，**没有单条改、删接口**；待发提示随后被编辑或发出，都不影响已保存的记录快照。
- 场次对照（`GET /api/compare`）是纯查询：不携带版本号、不加写锁，不修改档案、当前演出或版本号，开场前 / 演出中 / 已完成任意状态都可随时调用。
- 档案弹窗内的加载（列表 / 详情 / 对照）按视图序号防止过期响应覆盖：进入任一视图或关闭弹窗时序号 +1，请求记录发起时的序号，响应返回时序号不符即丢弃——关闭重开、返回列表、快速切换场次等交错场景下，旧响应不会恢复默认选择、不会把对照页替换成列表、也不会显示已过期的错误。
- **单控制席**：默认未启用，全部写接口保持旧行为（无需凭据）。`POST /api/control/enable`（仅未启用时）与 `POST /api/control/takeover`（仅已启用时）都携带页面版本号，在锁内检查版本后把「启用/换发凭据 + 版本号 +1」**同一事务**落库——同版本的启用、接管与业务写操作**最多一个成功**，过期版本返回 `409` 及最新状态，失败保留原控制席与版本。
- 启用后，手工开场、确认、编辑、重排、暂停/恢复、归档、重置、以档案开新场、问题记录**全部写接口**都校验请求头 `X-Control-Token`：**身份检查与业务写入在同一把锁、同一事务内生效**，不会出现"旧请求先通过检查、接管后再落库"的交错；凭据缺失或已被接管替换时返回 `403`（附最新状态）且**数据不变**，旧席即使用最新版本号也不能写。
- 接管**不改变**提示、进度、暂停标记与档案；凭据只随成功的启用/接管响应返回一次，**状态查询永不包含凭据**；所有查询接口始终可用、无需凭据。凭据与启用状态存于数据库，跨场、刷新、重启服务都保留。
- **控制资格核验**：`GET /api/state` 接受可选的 `X-Control-Token` 请求头，响应的 `control_granted` 字段如实回报**本请求**是否具备控制资格（未启用时恒为 `true`；启用后须凭据与当前控制席一致）。核验是**纯查询**：缺失或失效凭据同样返回 `200`，响应不含凭据，也不改变业务状态或版本号。所有状态响应（含写请求成功、`403`、`409` 附带的状态）都带 `control_granted`，页面据此更新资格标记与写入口——被接管后的旧标签页刷新即只读，无需先触发一次 `403`。
- **本场核验**：默认关闭，所有接口保持旧行为。`POST /api/verify/enable` 仅**开场前**可用，携带页面版本号、受单控制席保护（启用控制席后须携带 `X-Control-Token`），「启用标记 + 版本号 +1」在同一事务内落库——已启用、非开场前或版本过期返回 `409` 及最新状态，同版本的启用与其他写操作最多一个成功。
- **就绪回报**（`POST /api/verify/report`）提交工种（`lighting` / `sound`）、`cue_id`、轮次与就绪布尔值：**无需控制凭据**（即使已启用控制席）、**不携带也不改变全局版本号**。接口接受**可选**请求头 `X-Control-Token`：缺失或已被接管替换的凭据都可回报、**不返回 `403`**（仅不具备控制资格）；成功响应与 `409` 附带状态中的 `control_granted` 一律按**本次请求凭据**如实回报（响应永不包含凭据本身）——当前控制席回报后资格与缓存凭据保留，被接管旧页的成功/`409` 响应均回报 `false`，旧页据此清除失效缓存。仅核验已启用且**演出中（含暂停）**时接受对**当前提示 + 当前轮次**的回报；同工种同轮次重复回报覆盖写（以最后一次为准）。核验未启用、非演出中、轮次或提示已过期都返回 `409` 及最新状态且**不写入回报**；工种取值非法返回 `400`。
- **就绪门槛**：启用核验后，`POST /api/confirm` 还要求两工种对当前轮次**均已报就绪**，缺任一即使用最新版本号也返回 `409` 及最新状态（暂停规则不变，暂停时同样不能发出）。
- **轮次推进**：确认推进、撤回末条、改写当前提示（待发队首）、重排更换当前提示都会**开启新轮次（+1）并清空本轮就绪**，与业务写入在**同一事务**内提交——写入失败则轮次、就绪、提示、版本全部不变，不留部分结果。轮次单调递增、**不可复用**：旧轮次的回报因轮次不符被 `409` 拒绝。编辑其他待发提示、暂停/恢复、启用/接管控制席、记现场问题**不开启新轮次、不清空就绪**。撤回与确认同版本竞争仍最多一个成功：**撤回先完成则确认因版本过期失败，确认先完成则旧轮次撤回被拒**，双方都不会复用旧轮次。
- 核验的轮次与就绪记录随数据库持久化：**刷新页面、重启容器/服务都保留**；**归档或重置会关闭核验并清空轮次与就绪**（与收场写入同一事务），**下一场不继承**，档案结构与内容不变（核验数据不写入档案）。旧版本数据库启动时自动补上核验列与就绪记录表，默认关闭。
- **自动发出**（`POST /api/auto`）携带页面版本号并在锁内检查：仅**演出中**可设置，成功「开关 + 间隔 + 计时 + 版本 +1」在同一事务内落库；非演出中或版本过期返回 `409` 及最新状态，间隔非 1～60 整数返回 `400`（先于版本检查，不改数据）。开启或改间隔后**从完整间隔重新计时**；已开启时仅改间隔同样重计，开关与间隔都未变的调用不重置计时（仍推进版本）。后台定时任务与手工操作**共用同一把写锁**：执行时重新核对开关、演出状态、暂停标记、计时到期与两工种就绪——与手工确认竞争时，要么手工先生效（计时被重置，到期检查落空），要么自动先发出（手工确认因版本过期被 `409` 拒绝），**不会重复发出或跳条**。自动发出沿用手工确认的内容快照、`issued_seq = 新版本号` 与换轮规则；**每次只发一条**，下一条从完整间隔重新计时，**不补发积压**；到期未就绪继续等（不重置计时）。暂停/恢复把「冻结剩余时间 ↔ 续计」与暂停标记同一事务落库；手工确认、撤回、改写当前提示、重排换头在各自事务内一并重置计时，队首不变的重排与编辑其他提示不重置。接管、归档、重置、完成（含自动发出最后一条）在各自事务内关闭自动模式；**服务重启一律关闭**（间隔保留）。任何写入失败整体回滚：不推进、不重置计时、不改版本。自动模式的开关与计时随数据库持久化，但重启即关闭；页面轮询（`GET /api/state`）是纯查询，不参与并发控制。
- **改写提议**：见上方「并发与一致性规则 / 改写提议（提交 / 接受 / 拒绝）」专节——提交不经凭据、不改版本；接受须快照一致且与版本 +1 同事务（当前提示并重开轮次、重计时），拒绝不改版本；版本过期 / 已处理 / 目标失效一律 `409` 附最新状态且提议不变；归档、重置、开新场同一事务清空，不进档案。
- **观众字幕设置**（`POST /api/subtitles`）：携带页面版本号并在锁内检查，受单控制席保护（缺失 / 失效凭据 `403` 附最新状态且不变）。请求体 `{version, cue_id, subtitle}`：`subtitle` 为字符串时去除首尾空白后须为 **1～200 字符**，为 `null` 时清除该提示的字幕设置；空白、超长或非字符串（数字 / 数组 / 对象）返回 `400`（先于版本检查，用 `Any` 模型承接非法类型，统一中文错误而非 pydantic 的 `422`）。仅**演出中（`live`，含暂停）**且 `cue_id` 仍是**待发**时接受：开场前、已完成、目标不存在或已发出、版本过期一律 `409` 附最新状态，原有设置与有效性不变。「写入字幕设置（新设置标记有效）+ 版本 +1」在同一事务提交，但**不推进提示、不开启新核验轮次 / 清空就绪、不重新自动计时、不改变暂停状态，也不改变观众当前画面**（画面只随实际发出 / 撤回 / 收场变化）。
- **字幕绑定与失效**：字幕保存在 `cues.subtitle`（未设置为 `NULL`）、有效性在 `cues.subtitle_valid`，按**提示身份**绑定而非按文本。手工编辑（`/api/edit`）或接受提议（`/api/suggestions/{id}/accept`）改写某条提示时，在同一事务无条件把该提示的 `subtitle_valid` 置 0——**即使新文本与原文相同也失效**（设置文本保留，执行台仍可见并可重新设置）；**重排、暂停 / 恢复、记现场问题、提交 / 拒绝提议、撤回都不改变任何字幕的有效性**。撤回把提示退回待发时保留其字幕与有效性，再次发出仍按规则上屏。
- **发出与画面**：手工确认与后台自动发出共用同一个 `issue_current`：在「内容快照 + 推进 + 版本 +1 + 换轮 + 计时安排」的同一事务内，按被发出提示的 `subtitle_valid / subtitle` 计算新画面（有效则取字幕文本，否则 `NULL`），写入 `meta.screen_text` 并令 `meta.screen_seq + 1`（**无论上屏还是清屏，每次发出都是一帧新画面**）。任一步失败随事务整体回滚：提示不推进、画面不更换、版本不增加；字幕设置从不阻止发出（无字幕或失效即清屏发出）。
- **画面序号与清屏**：`meta.screen_seq` **跨场单调递增、从不归零**。撤回 / 归档 / 重置 / 手工录入新场 / 以档案开新场都在各自事务内清屏；其中**画面当前非空时才把序号 +1**（画面本就空白不重复制造空序号——序号标识更新的画面内容；只要画面上还显示着旧字幕，任何清屏路径都会推进序号，观众屏一定能看到清屏）。撤回**只清屏、不删字幕设置**；归档、重置与两类开新场随 `DELETE FROM cues` 一并删除字幕设置，且**不写入档案**（档案 JSON 结构、`/api/archives*` 与 `/api/compare` 响应均不含字幕字段）。
- **观众只读接口**（`GET /api/screen`）：纯查询，不加写锁、不要版本号与凭据，响应体**只有** `{subtitle, seq}` 两个字段（不含提示正文、编号、进度、状态、版本号、控制席、核验、自动、问题、提议等任何后台信息）。字幕屏页面每秒轮询且不重叠发请求；**只接受 `seq` 严格大于已显示序号的响应**，相同 / 更小序号（乱序、重试、跨场迟到的旧帧）一律丢弃，因此迟到响应**不能倒退画面**；网络 / HTTP 错误只显示断线提示并保留最后一帧，不自动清屏。`/screen` 页面本身是独立静态页（FastAPI 显式路由，先于静态目录挂载），只引用 `screen.js` 轮询该接口。
- **持久化与旧库**：字幕设置、有效性、观众画面与序号随 SQLite 持久化，**刷新、重启容器 / 服务都保留**（重启不关闭字幕，与自动模式不同；设置属于本场数据）。旧版本数据库启动时经 `ALTER TABLE` 自动补列：`cues.subtitle TEXT`、`cues.subtitle_valid INTEGER NOT NULL DEFAULT 0`、`meta.screen_text TEXT`、`meta.screen_seq INTEGER NOT NULL DEFAULT 0`，旧库默认无设置、空画面、序号 0，可直接使用。

### 本次修复：核验回报按钮请求结束后一直禁用

- **现象**：同页启用单控制席与本场核验、录入两条提示并开场后，开场虽然成功，灯光 / 音响的「报就绪」按钮一直灰掉无法点击；任意一次回报（成功或失败）后按钮也可能不再恢复。
- **原因（纯前端）**：回报按钮的 `disabled` 只在核验卡片重建（`renderVerify`）时按当时的在途标记 `busy` 写入；而开场 / 回报响应恰好在 `busy` 仍为 `true` 时触发渲染，随后 `busy` 复位只调用了同步其他按钮的 `updateBusy()`，没有任何逻辑把回报按钮恢复；反过来，回报请求发出时也未及时禁用按钮，快速连点会重复回报。
- **修复（仅 `app/static/app.js` 请求与按钮状态衔接，未改接口语义）**：
  - 新增统一的回报资格判定 `canVerifyReport()`（核验启用 + 演出中 + 有当前提示；不看控制资格，暂停允许，完成 / 关闭不允许）与 `updateVerifyButtons()`，按**最新状态 + 在途标记**重算两个真实渲染按钮的 `disabled`；
  - 请求在途两个按钮统一禁用防重复；`api()` 的 `finally`（成功、`409` 已刷新最新状态、`400/网络失败`）与卡片重建后都会重新同步——成功、`409` 刷新、请求失败均不再卡死按钮；开场成功后的首次渲染也由 `busy` 复位路径恢复；
  - 未构造"始终可用"的按钮：`reportVerify()` 以同一资格判定兜底，禁用按钮的真实点击不会发请求；确认仍须本页有控制权、两工种就绪且未暂停。
- **接口不变**：`POST /api/verify/report` 仍提交 `department`、`cue_id`、`round`、`ready` 与可选 `X-Control-Token`，响应语义（成功状态、`409` 附最新状态、`400`、永不 `403`）不变；当前席有效凭据仍随请求提交并在成功 / `409` 后保留，不会被误清。
- **回归命令**：`node tests/verify.test.js`（新增 T12–T15，断言全部读取真实渲染出的按钮 `disabled`，并经"回退修复后 22 处断言失败"验证有效）；其余前端回归 `node tests/control-seat.test.js`、`node tests/archive-modal.test.js`；后端回归 `python3 tests/verify.test.py` 等（需 `pip install -r requirements.txt`）。

### 本次修复：回报与待发重排交错时，回报未结束却被重排收尾提前解禁

- **现象**：同页拥有控制权、核验开启且有当前提示时，点击灯光「报就绪」后再点待发 ↑/↓ 重排；重排先失败（如 409 或网络错误）时，灯光 / 音响两个回报按钮就恢复可点——此时回报请求其实还未结束，再点灯光会重复提交相同回报。
- **原因（纯前端）**：在途标记 `busy` 是全部请求共用的单一布尔：回报与重排同时在途时，谁先结束谁的 `finally` 就把 `busy` 复位为 `false`，把另一个仍在途请求的占用提前解开，回报按钮与 `reportVerify()` 的入口守卫随之失效。
- **修复（仅 `app/static/app.js` 请求与按钮衔接，未改接口语义）**：
  - 在途标记改为**计数**（`busyCount` + `busyEnter()` / `busyLeave()`）：每个请求开始占一份、结束只释放自身一份；任一请求仍在途时 `busy` 保持为真——两工种回报按钮保持禁用、`reportVerify()` 提交入口继续拒绝回报；计数归零后才按**当时最新状态**恢复；
  - 成功、`409` 刷新、HTTP 错误（如 400）、网络失败四种结束方式都走同一 `finally` 释放路径：不会提前解禁，也不会永久锁住；
  - 回报资格判定（核验启用 + 演出中 + 有当前提示）、暂停可回报、确认就绪门槛、当前席有效凭据保留等行为均不变。
- **接口不变**：`POST /api/verify/report` 仍提交 `department`、`cue_id`、`round`、`ready` 与可选 `X-Control-Token`，响应语义（成功状态、`409` 附最新状态、`400`、永不 `403`）不变。
- **回归命令**：`node tests/verify.test.js`（新增 T16–T17：两请求可控响应覆盖"重排先结束 / 回报先结束"两种顺序，断言真实渲染按钮的 `disabled` 与回报请求数量，并经"回退修复后 11 处断言失败"验证有效）；其余前端回归 `node tests/control-seat.test.js`、`node tests/archive-modal.test.js`；后端回归 `python3 tests/verify.test.py` 等（需 `pip install -r requirements.txt`）。

> 启用控制席后，以上**全部 POST 写接口**（不含 `/api/control/*`、工种回报 `/api/verify/report` 与改写提议提交 `/api/suggestions`）都须携带请求头 `X-Control-Token`；缺失或已失效返回 `403`（附最新状态）且数据不变。`/api/verify/report` 与 `/api/suggestions` 不校验控制资格（缺失 / 失效凭据都不返回 `403`，只读页也能回报就绪、提交提议），但都接受可选的该请求头，以便成功 / `409` 响应按本次凭据回报 `control_granted`；接受 / 拒绝提议（`/api/suggestions/{id}/accept|reject`）与字幕设置（`/api/subtitles`）仍是控制席写操作，必须携带有效凭据。未启用时所有接口保持旧行为，无需该请求头。观众接口 `GET /api/screen` 与页面 `/screen` 始终公开只读，不接受也不需要凭据。

## 单控制席（请求示例）

默认未启用，写接口无需凭据。任意页面凭当前版本号启用（版本号见页面右上角 `vN` 或 `GET /api/state` 的 `version`）：

```bash
# 启用单控制席（仅未启用时）；成功返回随机凭据，仅此一次
curl -X POST http://localhost:8000/api/control/enable \
  -H 'Content-Type: application/json' \
  -d '{"version": 5}'
```

成功（`200`）返回最新状态 + 一次性凭据（`version` 在原版本上 +1）：

```json
{
  "version": 6,
  "status": "live",
  "paused": false,
  "control_enabled": true,
  "control_granted": true,
  "control_token": "9dB1xQ…随机凭据…kQ2w"
}
```

此后所有写操作都要在请求头带上该凭据（查询接口始终不需要）：

```bash
# 带凭据的写调用示例：确认发出 / 暂停 / 归档
curl -X POST http://localhost:8000/api/confirm \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…随机凭据…kQ2w' \
  -d '{"version": 6}'

curl -X POST http://localhost:8000/api/pause \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…随机凭据…kQ2w' \
  -d '{"version": 7, "paused": true}'

curl -X POST http://localhost:8000/api/archive \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…随机凭据…kQ2w' \
  -d '{"version": 8, "name": "10 月 3 日晚场"}'
```

凭据缺失或已被接管替换时，写请求返回 `403` 且数据不变（`state` 为最新状态）：

```json
{
  "error": "forbidden",
  "message": "本页面不是当前控制席：写操作未生效，可凭最新版本号接管",
  "state": { "version": 8, "control_enabled": true, "control_granted": false }
}
```

**查询时核验资格**（页面刷新即靠它纠正标记，无需先触发 403）：`GET /api/state` 接受可选的 `X-Control-Token` 请求头，响应的 `control_granted` 如实回报本请求的控制资格。核验是纯查询——凭据缺失或失效同样返回 `200`，响应永不包含凭据，也不改变业务状态或版本号：

```bash
# 无凭据查询：可用，control_granted 为 false（未启用控制席时恒为 true）
curl http://localhost:8000/api/state

# 提交缓存凭据核验：仍有效 → true；已被接管替换 → false
curl http://localhost:8000/api/state \
  -H 'X-Control-Token: 9dB1xQ…随机凭据…kQ2w'
```

```json
{
  "version": 8,
  "status": "live",
  "control_enabled": true,
  "control_granted": false
}
```

另一页面可凭**当前版本号**主动接管（无需旧凭据）；成功换发新凭据，旧凭据立即失效：

```bash
curl -X POST http://localhost:8000/api/control/takeover \
  -H 'Content-Type: application/json' \
  -d '{"version": 8}'
```

错误情况（启用与接管）：`409 {"error": "conflict", "message": "操作已过期", "state": {...}}`——已启用时再启用、未启用时接管，或版本号已过期（同版本已有其他操作先生效）；`state` 为最新状态，原控制席与版本不变。

## 本场核验（请求示例）

默认关闭，所有接口保持旧行为。下面是一套可直接执行的完整流程（假设服务运行在 `http://localhost:8000`，当前为开场前、版本号为 0）：

```bash
# 1) 开场前启用本场核验（携带当前版本号；启用控制席后须再加请求头 X-Control-Token）
curl -X POST http://localhost:8000/api/verify/enable \
  -H 'Content-Type: application/json' \
  -d '{"version": 0}'

# 2) 录入提示并开始演出（旧接口不变）；开场后核验从第 1 轮开始
curl -X POST http://localhost:8000/api/setup \
  -H 'Content-Type: application/json' \
  -d '{"cues": [{"number": "A1", "content": "灯光渐亮"}, {"number": "A2", "content": "音乐起"}]}'
```

启用后状态中会多出 `verify` 字段（`round` 为当前轮次、`cue_id` 为当前提示、两工种就绪状态，`null` 表示未回报）：

```json
{
  "version": 2,
  "status": "live",
  "verify": { "enabled": true, "round": 1, "cue_id": 1,
              "lighting": null, "sound": null, "all_ready": false }
}
```

```bash
# 3) 灯光、音响分别对"当前提示 + 当前轮次"报就绪
#    无需控制凭据、不携带版本号，也不改变全局版本号
curl -X POST http://localhost:8000/api/verify/report \
  -H 'Content-Type: application/json' \
  -d '{"department": "lighting", "cue_id": 1, "round": 1, "ready": true}'

curl -X POST http://localhost:8000/api/verify/report \
  -H 'Content-Type: application/json' \
  -d '{"department": "sound", "cue_id": 1, "round": 1, "ready": true}'

# 3b) 同时启用了单控制席时（可选）：回报仍不强制凭据——
#      无凭据页与被接管旧页不带 / 带旧凭据都能回报，不会收到 403；
#      但页面会自动把本页缓存的凭据放在 X-Control-Token 里一起提交，
#      成功与 409 响应中的 control_granted 即按这把凭据回报：
#      当前席为 true（资格保留、页面不转只读），旧凭据为 false（旧页清缓存）。
#      响应始终是状态本身，绝不包含凭据。
curl -X POST http://localhost:8000/api/verify/report \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…当前控制席随机凭据…kQ2w' \
  -d '{"department": "lighting", "cue_id": 1, "round": 1, "ready": true}'
# -> 200 {"version": 2, "control_enabled": true, "control_granted": true,
#         "verify": {"enabled": true, "round": 1, "cue_id": 1,
#                    "lighting": true, "sound": null, "all_ready": false}, ...}
# 旧凭据 / 无凭据同样 200（或过期时 409），只是 control_granted 为 false。

# 4) 两工种都就绪后确认发出（缺任一就绪时同样返回 409 及最新状态）
#    与回报不同，确认是控制席写操作：启用后必须携带当前凭据，否则 403
curl -X POST http://localhost:8000/api/confirm \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…当前控制席随机凭据…kQ2w' \
  -d '{"version": 2}'
```

确认成功后开启新轮次并清空本轮就绪（`verify` 变为 `{"enabled": true, "round": 2, "cue_id": 2, "lighting": null, "sound": null, "all_ready": false}`），下一提示需两工种重新报就绪。工种改变主意时可重复回报，以最后一次为准：`{"department": "lighting", "cue_id": 2, "round": 2, "ready": false}`。

错误情况：

- `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`：启用时——已启用、非开场前或版本过期；回报时——核验未启用、非演出中、轮次或 `cue_id` 已过期（确认推进 / 撤回 / 改写当前提示 / 重排换头都会开启新轮次，过期回报**不写入**、不改版本）；确认时——暂停中或两工种未全部就绪（`message` 为「灯光、音响尚未全部就绪，不能确认发出」）。`state` 均为最新状态，回报接口的成功与 `409` 状态都按本次请求携带的 `X-Control-Token` 回报 `control_granted`（不含凭据本身）；
- `400 {"error": "工种须为 lighting（灯光）或 sound（音响）"}`：回报工种取值非法，不改任何数据；
- `403`：启用控制席后，`/api/verify/enable` 与确认等旧写接口仍须携带有效的 `X-Control-Token`。**回报接口 `/api/verify/report` 永远不返回 `403`**：凭据缺失或已被接管替换时仍可正常回报，只是响应的 `control_granted` 为 `false`（旧页据此清除失效缓存、转只读，但不影响其继续报就绪）。

## 自动发出（请求示例）

默认关闭。演出中设置统一间隔（1～60 秒整数）与开关；携带页面版本号（右上角 `vN` 或 `GET /api/state` 的 `version`），启用控制席后须再加请求头 `X-Control-Token`：

```bash
# 开启自动发出：间隔 15 秒（成功版本 +1，从完整 15 秒重新计时）
curl -X POST http://localhost:8000/api/auto \
  -H 'Content-Type: application/json' \
  -d '{"version": 3, "enabled": true, "interval": 15}'

# 演出中改间隔（同样从完整间隔重新计时）；只改开关可省略 interval（沿用已设间隔）
curl -X POST http://localhost:8000/api/auto \
  -H 'Content-Type: application/json' \
  -d '{"version": 4, "enabled": true, "interval": 30}'

# 关闭自动发出（保留已设间隔，便于再次开启）
curl -X POST http://localhost:8000/api/auto \
  -H 'Content-Type: application/json' \
  -d '{"version": 5, "enabled": false}'
```

成功（`200`）返回最新状态，`auto` 字段包含开关、间隔、剩余秒数与等待就绪标记：

```json
{
  "version": 4,
  "status": "live",
  "auto": { "enabled": true, "interval": 15,
            "remaining_seconds": 15.0, "waiting_ready": false }
}
```

开启后**无需页面保持打开**：服务端后台任务在当前提示等满间隔、未暂停且（启用核验时）两工种均已报就绪时自动发出一条，规则与手工确认一致（内容快照、版本 +1、开启新轮次），随后从完整间隔计下一条；`remaining_seconds` 随每次状态查询刷新，暂停时显示冻结的剩余时间，到期未就绪时 `waiting_ready` 为 `true`（继续等，就绪后随即发出）。手工确认、撤回末条、改写当前提示或重排换头都会重新计时；接管、归档、重置、全部发出完成或服务重启会关闭自动模式（间隔保留）。

错误情况：

- `400 {"error": "自动间隔须为 1～60 秒的整数"}`：间隔非法（含小数、布尔、字符串、越界），先于版本检查，不改任何数据；
- `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`：当前不是演出中（开场前 / 已完成），或版本号已过期；`state` 为最新状态；
- `403`：启用控制席后未携带有效 `X-Control-Token`，数据不变。

## 改写提议（请求示例）

演出中（含暂停时）**任何页面**都可为待发提示提交改写建议；是否启用控制席都能提交，提交不需要凭据、不改版本号。控制席随后在待审提议上接受或拒绝。

```bash
# 1) 无控制权页面提交改写建议：cue_id 为待发提示 id，version 为页面所见版本号
#    （不携带 X-Control-Token；若本页缓存了凭据，也可随头提交，仅用于回报资格）
curl -X POST http://localhost:8000/api/suggestions \
  -H 'Content-Type: application/json' \
  -d '{"version": 5, "cue_id": 3, "content": "音乐提前两拍起，灯光再压暗一档"}'
```

成功（`200`）返回**当前完整状态**（版本号不变，`suggestions` 中多出一条待审提议）：

```json
{
  "version": 5,
  "status": "live",
  "control_enabled": true,
  "control_granted": false,
  "suggestions": [
    {
      "id": 1,
      "cue_id": 3,
      "cue_number": "A3",
      "original_content": "幕落",
      "content": "音乐提前两拍起，灯光再压暗一档",
      "status": "pending",
      "target_valid": true,
      "created_at": "2026-10-05T19:30:00.000000+00:00",
      "decided_at": null
    }
  ]
}
```

字段说明：`original_content` 是提交时的**原文快照**；`target_valid` 为派生字段，表示"现在接受能否生效"——目标仍待发且当前内容等于快照时为 `true`，其他提示编辑、暂停、重排不影响它，只有该提示自身被改写或已发出才变为 `false`（已处理的提议该字段恒为 `false`）。

```bash
# 2) 控制席审核（启用控制席后须携带凭据；未启用时无需该头）
#    接受：目标须仍待发且内容等于原文快照；成功版本 +1
curl -X POST http://localhost:8000/api/suggestions/1/accept \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…当前控制席随机凭据…kQ2w' \
  -d '{"version": 5}'

#    拒绝：仅标记已拒绝，不改提示、不改版本
curl -X POST http://localhost:8000/api/suggestions/1/reject \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…当前控制席随机凭据…kQ2w' \
  -d '{"version": 5}'
```

接受成功（`200`）返回最新状态：目标提示内容已改为建议、提议变为 `accepted`、`version` 在原版本上 +1（接受的是当前待发队首时，同时重开核验轮次、重新自动计时）：

```json
{
  "version": 6,
  "status": "live",
  "suggestions": [
    { "id": 1, "status": "accepted", "target_valid": false,
      "decided_at": "2026-10-05T19:31:02.000000+00:00" }
  ]
}
```

拒绝成功（`200`）返回最新状态但**版本号不变**（提议 `status` 已为 `rejected`）。错误情况：

- `400 {"error": "内容不能为空"}`：建议去除首尾空白后为空，不改任何数据；
- `404 {"error": "cue_not_found"}`：提交时 `cue_id` 不存在；
- `403`：启用控制席后，**接受 / 拒绝**未携带有效 `X-Control-Token`（提交 `/api/suggestions` 永远不返回 `403`）；
- `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`：
  - 提交时——开场前、非演出中、目标已不是待发，或版本过期；
  - 接受时——版本过期、提议不存在或已处理（已被接受 / 拒绝）、目标已发出或内容已不等于原文快照；此时**提议保持待审核不变**，不会覆盖已变化的内容（可改用拒绝）；
  - 拒绝时——版本过期、提议不存在或已处理。
  - 所有 `409` 都附带最新状态，页面据此刷新提议列表与版本号。

## 观众字幕屏（双页使用与请求示例）

执行台页（`http://主机:8000/`）与观众字幕屏（`http://主机:8000/screen`）是**两个相互独立的页面**：观众设备（投影旁的小屏、平板、第二块标签页）只打开 `/screen`，整页只有字幕；提示正文、编号、核验、自动发出、档案等后台信息只在执行台页，观众页及其接口都拿不到。

### 执行台设置字幕（`POST /api/subtitles`）

演出中（含暂停）对任意**待发提示**设置字幕。携带页面版本号（右上角 `vN` 或 `GET /api/state` 的 `version`）与目标 `cue_id`；启用控制席后还须加 `X-Control-Token`：

```bash
# 为待发提示 3 设置字幕（去除首尾空白后须为 1～200 字符）
curl -X POST http://localhost:8000/api/subtitles \
  -H 'Content-Type: application/json' \
  -H 'X-Control-Token: 9dB1xQ…当前控制席随机凭据…kQ2w' \
  -d '{"version": 5, "cue_id": 3, "subtitle": "  第三幕：暴风雨夜  "}'

# 清除该提示的字幕设置
curl -X POST http://localhost:8000/api/subtitles \
  -H 'Content-Type: application/json' \
  -d '{"version": 6, "cue_id": 3, "subtitle": null}'
```

成功（`200`）返回当前完整状态：设置与 `version` +1 同事务落库，**不推进提示、不换核验轮次、不重新计时、当前画面不变**。待发条目里带有字幕设置与有效性，顶层 `screen` 是观众屏当前画面：

```json
{
  "version": 6,
  "status": "live",
  "current": { "id": 3, "number": "A3", "content": "幕落（后台提示正文）" },
  "pending": [
    { "id": 3, "number": "A3", "content": "幕落（后台提示正文）",
      "subtitle": "第三幕：暴风雨夜", "subtitle_valid": true }
  ],
  "screen": { "subtitle": null, "seq": 0 }
}
```

要点：

- 字幕**绑定 cue_id**：之后用 `/api/edit` 手工改写或接受 `/api/suggestions/{id}/accept` 改写该提示，**即使文本一字不差**，`subtitle_valid` 也变为 `false`（执行台显示「字幕已失效」，字幕文本保留）；**重排、暂停、记问题不影响有效性**。
- 观众画面**只随发出变化**：提示被手工或自动发出时，有效字幕才上屏（或失效 / 无字幕时清屏）；`POST /api/subtitles` 本身不动画面，因此上面的 `screen.seq` 仍为 0。

错误情况：

- `400 {"error": "字幕去除首尾空白后需为 1～200 字符"}`：空白、超长或 `subtitle` 不是字符串（数字 / 数组 / 对象），先于版本检查，不改数据；
- `409 {"error":"conflict","message":"操作已过期","state":{…}}`：开场前 / 已完成等非演出状态、目标不存在或已不是待发（刚被发出等）、版本过期；`state` 为最新状态，原设置与版本不变；
- `403`：启用控制席后未携带有效凭据，设置不生效。

### 发出 / 撤回 / 收场时画面如何变化

```bash
# 提示 3 带着有效字幕被确认发出：画面替换为字幕，画面序号 +1
curl -X POST http://localhost:8000/api/confirm \
  -H 'Content-Type: application/json' \
  -d '{"version": 7}'
# -> 200，state.screen = {"subtitle": "第三幕：暴风雨夜", "seq": 1}
#    （自动发出走同一实现，画面同样更新；字幕已失效时这里是 {"subtitle": null, "seq": n}）

# 撤回末条：清屏（画面非空时序号 +1），但字幕设置保留
curl -X POST http://localhost:8000/api/withdraw \
  -H 'Content-Type: application/json' \
  -d '{"version": 8, "cue_id": 3}'
# -> 200，state.screen = {"subtitle": null, "seq": 2}；
#    提示 3 回到待发队首，仍带着它的字幕设置与有效性，再次发出照常上屏
```

归档、重置、手工录入新场、以档案开新场都会**清屏并清除字幕设置**（字幕不进档案，档案接口的 JSON 里没有字幕字段）；`seq` 跨这些操作继续递增、**从不归零**。

### 观众屏只读接口（`GET /api/screen`）

无需任何凭据或版本号，响应永远只有两个字段：

```bash
curl http://localhost:8000/api/screen
# 有字幕时
# {"subtitle":"第三幕：暴风雨夜","seq":1}
# 清屏时（开场前、失效字幕发出后、撤回 / 收场后）
# {"subtitle":null,"seq":2}
```

`/screen` 页面每秒轮询这个接口，并且**只接受 `seq` 严格变大的响应**：乱序或迟到的旧响应（例如清屏后一个 `seq=1` 的响应才到）直接丢弃，画面不会从清屏倒退回旧字幕、也不会从新字幕倒退成旧字幕；请求失败时保留最后一帧字幕并显示「连接中断，正在重试…」，不自动清屏。因为接口只暴露字幕本身，观众即使查看页面源码也无法获得提示正文等后台数据。

## 暂停 / 恢复发出（请求示例）

演出页右上角可见当前页面版本号（`vN`），暂停与恢复都提交**目标状态** `paused` 与该版本号：

```bash
# 暂停发出
curl -X POST http://localhost:8000/api/pause \
  -H 'Content-Type: application/json' \
  -d '{"version": 5, "paused": true}'

# 恢复发出
curl -X POST http://localhost:8000/api/pause \
  -H 'Content-Type: application/json' \
  -d '{"version": 6, "paused": false}'
```

成功（`200`）返回最新状态：`paused` 已切换为目标值、`version` 在原版本上 +1，`status` 取值不变（仍为 `live`）：

```json
{
  "version": 6,
  "status": "live",
  "paused": true,
  "current": { "id": 2, "number": "A1", "content": "灯光渐亮" },
  "remaining": 3
}
```

错误情况（均返回 `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`，`state` 为最新状态）：

- 当前不是演出中（开场前 / 已完成）；
- 目标已达成（已暂停时再暂停、未暂停时再恢复）；
- 版本号已过期（同版本已有暂停/恢复/确认/编辑先生效）。

暂停期间 `POST /api/confirm` 即使用最新版本号也返回 `409` 及最新状态；`/api/edit`、`/api/reorder`、`/api/withdraw`、`/api/archive` 不受影响，`/api/issues` 在暂停时同样可以记录。

## 撤回末条（请求示例）

误点确认后，可把**本场最后一条已发提示**退回当前待发，不撤销其他操作。提交页面所见的末条已发 `cue_id`（状态 JSON 中 `issued` 数组最后一个元素的 `id`）与版本号：

```bash
# version 为页面所见版本号；cue_id 为最后一条已发提示的 id
curl -X POST http://localhost:8000/api/withdraw \
  -H 'Content-Type: application/json' \
  -d '{"version": 6, "cue_id": 2}'
```

成功（`200`）返回最新状态：该提示以**发出时的内容快照**成为**当前待发**（`current`，位于 `pending` 队首），保留原 id 与编号；其发出快照、发出时间、发出序号已清除，因此不再出现在 `issued` 中；**其他已发记录、其余待发内容与相对顺序、问题记录快照均不变**；`version` 在原版本上 +1。已完成态撤回后 `status` 由 `done` 回到 `live`；暂停标记 `paused` 不变：

```json
{
  "version": 7,
  "status": "live",
  "paused": false,
  "current": { "id": 2, "number": "A2", "content": "音乐起" },
  "next": { "id": 3, "number": "A3", "content": "幕落" },
  "pending": [
    { "id": 2, "number": "A2", "content": "音乐起" },
    { "id": 3, "number": "A3", "content": "幕落" }
  ],
  "issued": [
    { "id": 1, "number": "A1", "content": "灯光渐亮", "issued_at": "2026-10-04T10:00:00.000000+00:00" }
  ],
  "remaining": 2
}
```

随后再次确认该提示时，服务端记录**新的发出时间**（不复用撤回前的时间）。页面上已发记录标题右侧的「撤回末条 ↩」会先弹二次确认，确认后才发请求；没有已发记录、开场前或本页不是控制席时按钮禁用。

错误情况（均返回 `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`，`state` 为最新状态，**数据不变**）：

- 当前为开场前（`setup`），或本场没有已发提示；
- `cue_id` 不是**最后一条**已发提示（例如该条已被先撤回、或其后又发出了新提示）——不支持跳过末条撤回更早的提示，也不提供批量撤回；
- 版本号已过期（同版本已有确认／编辑／重排／撤回／暂停恢复／归档／问题记录先生效）。

启用控制席后，撤回同样要携带 `X-Control-Token`：凭据缺失或已被接管替换返回 `403`（附最新状态）且数据不变。撤回结果保存在数据库中，刷新页面、重启容器/服务都保留；**既有档案不做任何修改**。

## 现场问题记录（请求示例）

演出中（含暂停时）或全部发出后，为本场**任意一条提示**（已发或待发）追加现场问题。提交页面所见版本号、提示 `cue_id` 与正文：

```bash
curl -X POST http://localhost:8000/api/issues \
  -H 'Content-Type: application/json' \
  -d '{"version": 5, "cue_id": 2, "text": "A2 音乐比灯光晚了约 2 秒，演员略有停顿"}'
```

成功（`200`）返回最新状态：`version` 在原版本上 +1，提示进度与 `paused` 均不变；新增的记录出现在 `issues` 数组末尾（**按保存顺序**）。每条记录包含服务端保存时间、当时编号、已发／待发状态与当时内容（已发为发出快照），以及去除首尾空白后的正文：

```json
{
  "version": 6,
  "status": "live",
  "paused": false,
  "issues": [
    {
      "id": 1,
      "cue_id": 2,
      "cue_number": "A2",
      "cue_status": "pending",
      "cue_content": "音乐起",
      "text": "A2 音乐比灯光晚了约 2 秒，演员略有停顿",
      "created_at": "2026-10-03T11:22:33.456789+00:00"
    }
  ]
}
```

已发提示（`"cue_status": "issued"`）的 `cue_content` 是该提示**发出那一刻的内容快照**，之后对其它提示的编辑、重排都不会改变它。问题记录随 `GET /api/state` 读取，并在归档后随 `GET /api/archives/{id}` 的 `issues` 字段一起回看。

错误情况：

- `400 {"error": "问题内容去除首尾空白后需为 1～200 字符"}`：正文去除首尾空白后为空或超过 200 字符（按字符计），**不改任何数据**；
- `404 {"error": "cue_not_found"}`：`cue_id` 在本场提示中不存在；
- `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`：当前为开场前，或版本号已过期（同版本已有确认／编辑／重排／暂停恢复／归档／另一条问题记录先生效），`state` 为最新状态。

记录一旦保存**不可单独修改或删除**；归档时随本场快照写入档案并清空当前记录，重置、手工录入新场、以档案开新场也会清空当前记录（以档案开新场不复制档案中的问题记录）。

## 以档案开新场（请求示例）

先在档案详情页看到目标档案 ID 与当前页面版本号（右上角 `vN`），然后：

```bash
# version 为页面所见版本号；id 为档案 ID
curl -X POST http://localhost:8000/api/archives/3/start \
  -H 'Content-Type: application/json' \
  -d '{"version": 7}'
```

成功（`200`）返回新场的完整状态：`status` 为 `live`、`issued` 为空、`current` 指向第一条（档案已发顺序首条；若档案没有已发则为剩余未发首条）、`version` 在原版本上 +1，提示内容即页面所见的快照版本。

```json
{
  "version": 8,
  "status": "live",
  "paused": false,
  "current": { "id": 4, "number": "A1", "content": "灯光渐亮" },
  "next": { "id": 5, "number": "A2", "content": "音乐起" },
  "pending": [
    { "id": 4, "number": "A1", "content": "灯光渐亮" },
    { "id": 5, "number": "A2", "content": "音乐起" }
  ],
  "issued": [],
  "total": 2,
  "remaining": 2
}
```

错误情况：

- `404 {"error": "archive_not_found"}`：档案不存在；
- `400`：拼出的提示不满足 2～12 条 / 编号唯一 / 内容非空（`error` 为中文原因）；
- `409 {"error": "conflict", "message": "操作已过期", "state": {...}}`：当前不是开场前，或版本号已过期；响应体中的 `state` 为最新状态。

## 场次对照（请求示例）

对照接口接收两个档案 ID（`base` 为基准场次、`compare` 为对照场次），是只读查询，无需版本号，任意演出状态可用：

```bash
curl 'http://localhost:8000/api/compare?base=1&compare=2'
```

成功（`200`）返回两场摘要与按编号字符串升序的并集明细：

```json
{
  "base":    { "id": 1, "name": "10 月 1 日晚场", "status": "done", "issued_count": 2, "pending_count": 1 },
  "compare": { "id": 2, "name": "10 月 2 日晚场", "status": "live", "issued_count": 2, "pending_count": 1 },
  "rows": [
    {
      "number": "A1",
      "base":    { "status": "issued",  "content": "灯光渐亮", "offset_seconds": 0.0 },
      "compare": { "status": "issued",  "content": "灯光渐亮", "offset_seconds": 0.0 },
      "delta_seconds": 0.0,
      "delta_reason": null
    },
    {
      "number": "A2",
      "base":    { "status": "issued",  "content": "音乐起", "offset_seconds": 12.5 },
      "compare": { "status": "issued",  "content": "音乐起", "offset_seconds": 15.25 },
      "delta_seconds": 2.75,
      "delta_reason": null
    },
    {
      "number": "A3",
      "base":    { "status": "pending", "content": "幕落", "offset_seconds": null },
      "compare": { "status": "missing", "content": null,   "offset_seconds": null },
      "delta_seconds": null,
      "delta_reason": "基准场未发出；对照场无此编号"
    }
  ]
}
```

字段说明：

- `rows[].base` / `rows[].compare`：该编号在基准场 / 对照场的一侧视图。`status` 为 `issued`（已发）/ `pending`（未发）/ `missing`（该场无此编号）；`content` 为内容快照（已发给出发出时的快照，缺失为 `null`）。
- `offset_seconds`：相对**本侧场次首条已发提示**发出时间的秒数（使用档案保存的发出时间，保留小数秒，暂停时长计入）；未发、缺失或整场无已发记录时为 `null`。
- `delta_seconds`：「对照 − 基准」的秒数差，**正值表示对照场更晚**；仅当两侧均已发出且内容完全相同时给出，其余为 `null` 并由 `delta_reason` 给出中文原因（未发出 / 无此编号 / 内容不一致等）。

错误情况：`404 {"error": "archive_not_found"}`——任一档案不存在。

## 项目结构

### 模块职责：`app/main.py` 与 `app/cueflow.py`

提示变更业务（会改动本场 `cues` 及联动状态的操作）集中在共用业务模块 **`app/cueflow.py`**，`main.py` 只保留 FastAPI 装配与 HTTP 薄壳：

- **`app/cueflow.py`（共用业务，不依赖 HTTP）**：`manual_issue`（手工确认）、`auto_issue_due`（后台自动发出）、`withdraw_last`（撤回末条）、`edit_pending`（编辑）、`reorder_pending`（重排）、`accept_pending_suggestion`（接受改写提议）、`set_pending_subtitle`（字幕设置 / 清除）、`clear_screen`（撤回 / 收场清屏），以及核验换轮 `verify_advance` 与自动计时 `restart_timer / freeze_timer / thaw_timer / disable_auto`。前置条件不满足抛 `Conflict`（HTTP 409）或 `BadRequest`（400）。函数只接收调用方已打开的 sqlite 连接，**自身不获取锁、不提交事务**；时钟以 `clock` 参数显式注入（生产传真实时间，测试传可控时钟）。
- **手工与自动共用同一个发出实现**：`manual_issue` 与 `auto_issue_due` 各自只做本路径的资格检查——手工查**版本、暂停、两工种就绪**（凭据由端点先查），自动查**开关、演出状态、暂停、计时到期、就绪且不需要任何客户端凭据**——通过后都调用同一个 `issue_current` 完成「内容快照入已发 + 推进一条 + 版本 +1 + 核验换轮 + 下一条完整间隔重计时（末条完成并关闭自动）+ **观众字幕上屏或清屏（画面序号 +1）**」，不是两份重复实现。字幕失效（编辑 / 接受提议时把该提示 `subtitle_valid` 置 0，即使同文）与清屏（`clear_screen`）也都在这些业务函数的同一事务内完成；归档 / 重置 / 开新场的端点经 `DELETE FROM cues` 连同字幕设置一起清除（不进档案）。
- **`app/main.py`（HTTP 薄壳）**：每个写端点在 `with lock, db() as conn`（同一把写锁、同一事务）内先做控制席身份检查（`control_check`，缺失 / 失效凭据 403），再调用 cueflow 并把 `Conflict / BadRequest` 映射为 409（附最新状态）/ 400。因此**身份、版本与发出资格检查始终与写入处于同一写锁、同一事务内**；提示快照、待发队列（位置）、版本号、提议状态、核验轮次 / 就绪、自动计时与**字幕设置 / 有效性 / 观众画面**随该事务**一起提交或回滚**。旧接口的 HTTP 方法、路径与状态码保持不变（待发条目新增 `subtitle` / `subtitle_valid`、状态新增 `screen` 均为附加字段），新增 `POST /api/subtitles`、`GET /api/screen` 与 `/screen` 页面。查询、状态组装、档案、场次对照、控制席启停、核验启用 / 回报、自动设置、提议提交 / 拒绝、观众只读画面、开场 / 归档 / 重置等不属于"提示变更"的操作仍在 `main.py`。
